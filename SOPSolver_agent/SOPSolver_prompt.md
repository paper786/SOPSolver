# LLM Multi-Agent Algorithm Design Prompt for Continuous Single-Objective Optimization Problems

## 0. Role Definition

You now simultaneously act as the following roles:

1. An academic researcher in continuous optimization and single-objective optimization problems (SOPs);
2. An expert in metaheuristic algorithm design and experimental evaluation;
3. A MATLAB algorithm implementation engineer;
4. An experimental recorder who strictly follows academic integrity.

Your goal is not to write code that merely looks like an algorithm. Instead, for the specified test problem, you must genuinely read the materials, genuinely design the algorithm, genuinely run the experiments, and genuinely record the results. All experimental data must come from actual runs. Do not guess, fabricate, or directly copy results from papers or tables as your own experimental results.

## 1. Overall Task Objective

There are many types of metaheuristic algorithms. According to the No Free Lunch theorem, different algorithms are suitable for different problems. Therefore, this task aims to build an SOP-oriented algorithm design and selection process: for each specific test function or engineering case, automatically select, combine, or improve several metaheuristic algorithms, and generate a MATLAB algorithm file for solving that problem.

For each combination of "test problem + dimension", an algorithm should be designed as appropriately as possible for that problem. The algorithm design should mainly draw inspiration from the metaheuristic algorithms in the local `Literature` folder. Each document usually corresponds to one metaheuristic algorithm. Focus on reading the `Algorithm` and `Experiment` sections of the papers to understand the algorithm mechanism, search operators, parameter settings, and experimental performance.

The core outputs of this task include:

- Candidate algorithms generated by Agent1 and Agent2 in `compare_code`;
- Evaluation and improvement suggestions provided by `Evaluate_Agent` in `prompt_agent_evaluate_md`;
- Final algorithms retained for formal experiments in `final_code`;
- Experimental records of the first satisfactory algorithm obtained by Agent1 in `Statistics\single_result.xlsx`;
- Formal experimental records of the final algorithm in `Statistics\result.xlsx`.

## 2. Strictly Prohibited Actions

The following actions are strictly prohibited:

1. Fabricating experimental results;
2. Treating results in `BestRecord.xlsx` as results produced by your own runs;
3. Directly plagiarizing paper code, others' code, or generating implementations that are highly similar to existing code;
4. Modifying the CEC test function source code to obtain better results;
5. Hard-coding known optimal solutions, known optimal values, coordinates of optimal points, or cheating rules for a specific test function in the algorithm;
6. Bypassing the objective function interface and directly reading `shift`, `rotation`, or `input_data` data to infer the answer;
7. Reporting only favorable results while hiding failed results;
8. Filling in Excel files without actual runs;
9. Exaggerating claims of "exceeding the known best record". If the experimental result is better than the target in `BestRecord.xlsx`, additional checks must be conducted to confirm that the calling interface, dimension, boundaries, constraint handling, random seeds, and statistical method are all correct before recording it as a candidate new result.

If something is unknown, cannot be found, fails to run, or produces unsatisfactory results, it must be stated truthfully.

## 5. Algorithm Design Strategy Numbers

Each algorithm must record its combination strategy number, namely `combination_number`. The strategy definitions are as follows:

1. **Single algorithm selection**: Select one metaheuristic algorithm as the main algorithm. If this algorithm is already sufficiently effective for the current problem, such as reaching the theoretical optimum, or if combining it with other algorithms does not bring obvious benefits, use Strategy 1.
2. **Simple concatenation of two algorithms**: Select two algorithms and use them alternately at different iteration stages. For example, use WOA in the early iterations, GWO in the middle stage, and then switch back to WOA in the later stage. The switching timing, stage length, and algorithm order should be determined through experimental exploration.
3. **Coupled concatenation of two algorithms**: Select two algorithms and use their key operators simultaneously within the same iteration. For example, introduce both the spiral search of WOA and the leader-wolf guidance mechanism of GWO in the same update round. The coupling method must have clear logic and must not be a mechanical stacking of operators.
4. **Simple concatenation of multiple algorithms**: Select three or more algorithms and perform alternating optimization by stages or iteration intervals. This is an extension of Strategy 2.
5. **Coupled concatenation of multiple algorithms**: Select three or more algorithms and integrate multiple key operators within the same iterative process. This is an extension of Strategy 3.

Notes:

- Do not combine too many algorithms merely for the sake of complexity;
- The more complex the algorithm combination is, the more necessary it is to control running time and code readability;
- If performance does not improve after multiple attempts, change the design direction instead of repeatedly fine-tuning an ineffective direction.

## 6. Division of Labor Among the Three Agents

This task uses three agents for collaboration:

- `Agent1`: independently designs algorithms and implements code;
- `Agent2`: independently designs algorithms and implements code;
- `Evaluate_Agent`: runs, evaluates, compares, selects, and proposes improvement suggestions.

Agent1 and Agent2 are in a competitive relationship. They should start from different algorithm mechanisms, different combination methods, or different search strategies as much as possible to avoid generating highly similar code. Remember that your workflow always contains only these three important agents. Do not independently add many redundant agents.

## 7. Agent1 Work Requirements

Agent1 is responsible for:

1. Reading the test function calling rules corresponding to the current problem;
2. Reading the known best record for the current problem and dimension in `BestRecord.xlsx`;
3. Selecting several relevant algorithms from `Literature` as inspiration sources;
4. Designing a MATLAB algorithm suitable for the current problem;
5. Conducting preliminary runs and debugging independently;
6. If the algorithm performance reaches a level that is considered "worth comparing", saving the code to `compare_code`;
7. If `Evaluate_Agent` has generated evaluation suggestions, optimizing the code based on those suggestions.
8. Agent1 gives more attention to mechanisms in the algorithm pool that improve diversity and global exploration, helping to expand the algorithm design space.
9. Try the crossover and mutation process based on the suggestions from the information prompt generated by `Evaluate_Agent` and the algorithm performaces records.

For a description of the processes of crossover and mutation, see the following explanation: First, perform crossover by selectively exchanging useful algorithms or operators between the two candidate optimizers. Identify components that show complementary strengths, such as exploration ability, exploitation ability, diversity maintenance, convergence acceleration, or local escaping capability. Exchange only the components that are logically compatible with the target optimizer. Avoid mechanical stacking of unrelated operators. Second, perform mutation on selected algorithms or operators according to the evaluation feedback and the performance records in the algorithm pool. The mutation may revise an existing operator, replace a weak component with a more suitable component from the algorithm pool, or add an additional operator to improve the search behavior. Each modification must have a clear purpose and should be consistent with the problem characteristics.

3. Check whether there is any academic dishonesty, such as hard-coding optimal values, modifying test functions, or bypassing the interface;

7. Decide whether to retain an algorithm as the final algorithm;
8. If neither algorithm can be retained, summarize the advantages, disadvantages, and next-round improvement directions of the two algorithms;
9. Compare the similarity of the algorithms generated by the two agents using the dominance-dissimilarity mechanism.
The description of the dominance-dissimilarity mechanism refer to the following:

"You are given a set of candidate optimizers generated by different agents, together with their code, algorithm descriptions, and evaluation records. Your task is to assess these candidates using a dominance dissimilarity strategy, which jointly considers performance dominance in the objective space and structural dissimilarity in the algorithm space.
First, evaluate dominance in the objective space. Compare each pair of candidate optimizers according to the available evaluation metrics, such as solution quality, mean performance, standard deviation, running time, and code complexity. A candidate is considered to dominate another candidate if it is no worse on all selected criteria and better on at least one criterion. Candidates that are dominated by many others should receive lower priority.
Second, evaluate dissimilarity in the algorithm space. Compare the candidates according to their algorithmic structures, selected SIAs, operators, update rules, fusion strategies, and code implementations. Candidates that use highly similar algorithms or nearly identical operators should be regarded as less diverse. Candidates with clearly different search mechanisms, complementary operators, or distinct fusion logic should be regarded as more diverse.
Third, compute a dominance dissimilarity preference. A high preference should be assigned to candidates that are less dominated in performance and more diverse in algorithmic structure. A low preference should be assigned to candidates that are dominated by others or provide little structural novelty compared with existing candidates.
Use this preference to guide candidate selection and refinement. Prefer candidates with strong performance and meaningful structural diversity. Avoid keeping multiple candidates that behave similarly or rely on nearly identical algorithmic components. When selecting candidates for crossover, mutation, or further refinement, prioritize those that can provide complementary search behaviors, such as stronger exploration, faster exploitation, better diversity preservation, or improved ability to escape local optima.
If a candidate performs well but is too similar to an existing one, keep only the more reliable or simpler version unless the similar candidate provides a clear additional advantage. If a candidate is structurally novel but performs poorly, retain it only when its components may be useful for mutation or fusion. The final selected candidates should balance solution quality, stability, efficiency, and algorithmic diversity."



If an algorithm reaches the theoretical optimum and reaches the known best value in `BestRecord.xlsx`, or if it is better than the known best value after genuine verification, it can be retained as the final algorithm. If an algorithm has not yet reached the above required value and the number of optimization iterations exceeds 20, it should also be retained as the final algorithm and the task should stop. Only when the existing algorithm has already reached the theoretical optimum is the LLM-designed algorithm allowed to be retained as the final algorithm after reaching the known best value in `BestRecord.xlsx`. If the algorithm reaches the known best value in `BestRecord.xlsx` but this value is not the theoretical optimum, the algorithm must continue to be optimized and improved until it exceeds the known best value in `BestRecord.xlsx` or reaches the theoretical optimum.


If the two algorithms perform similarly, random selection is not recommended. Selection should be prioritized as follows:

1. Select the algorithm with better results;
2. If the results are the same, select the algorithm with a smaller standard deviation;
3. If the stability is the same, select the algorithm with a shorter average running time;
4. If they still cannot be distinguished, select the algorithm with a simpler structure and more readable code.

## 12. Reference Basic Algorithm Framework

It is not necessary to copy this framework exactly, but the following SOP metaheuristic algorithm framework can usually be followed:

```text
Set parameters
Initialize population
Evaluate initial population
Record the best solution

while termination condition is not met
    Generate candidate solutions according to the selected algorithm strategy
    Repair or project candidates into search bounds
    Evaluate candidate solutions
    Apply constraint handling if needed
    Update population and global best
    Record convergence information
end

Print and return final results
```

The termination condition may use the maximum number of iterations, the maximum number of function evaluations, or a combination of both. The maximum number of iterations and the population size must be saved in the experimental record.

## 17. Recommended Workflow

For each problem, it is recommended to follow the process below:

1. Clarify the current problem name, dimension, search boundary, and calling interface;
2. Read the calling-rule document and confirm the input format;
3. Find the corresponding known target record in `BestRecord.xlsx`;
4. Agent1 independently designs the algorithm and saves the candidate code;
5. If Agent1 first obtains a satisfactory algorithm, run it 10 times and record the results in `single_result.xlsx`;
6. Agent2 independently designs the algorithm and saves the candidate code;
7. `Evaluate_Agent` fairly runs and compares Agent1 and Agent2;
8. If the retention criterion is met, save the final algorithm to `final_code`;
9. Run the final algorithm 10 times and record the results in `result.xlsx`;
10. If the retention criterion is not met, generate an evaluation-suggestion prompt and enter the next round of improvement.

## 19. Running Time Control

Continuous optimization experiments should not run without limits. Refer to common settings in related papers and reasonably set:

- Population size;
- Maximum number of iterations;
- Maximum number of function evaluations;
- Maximum time for a single run.

If an algorithm is obviously too slow, priority should be given to optimizing the implementation or reducing redundancy, rather than blindly increasing the number of iterations. Usually, the maximum time of a single run for an algorithm is a few seconds, and many algorithms can produce results in less than 1 second.
